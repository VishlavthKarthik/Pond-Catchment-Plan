Executive Summary

This report documents the end-to-end integration, deployment, and verification of OpenTelemetry (OTel) into the AI-based Village Pond & Catchment Planning System (HydroPond AI) from Assignment 1, deployed at http://10.1.75.51:3317/.

Modern backend systems require comprehensive observability beyond unstructured, isolated log messages. Using OpenTelemetry's vendor-neutral API and SDK, we instrumented all critical backend micro-stages: HTTP ingress routing, KML contour ingestion, Digital Elevation Model (DEM) rasterization, Wang-Liu priority-flood depression filling, D8 flow routing, upstream watershed delineation, and Central Water Commission (CWC) rational runoff calculations.

Observability data is continuously collected across the Three Pillars of Observability:

  • Distributed Tracing: Exported via OpenTelemetry Protocol (OTLP/HTTP) to a Jaeger distributed tracing engine (http://10.1.75.51:16686), capturing end-to-end span waterfalls, call trees, and custom domain attributes.
  • Application & Infrastructure Metrics: Aggregated via the OpenTelemetry MeterProvider and scraped at http://10.1.75.51:3317/metrics by a Prometheus Time-Series Database (http://10.1.75.51:9090), enabling real-time PromQL monitoring and capacity profiling.
  • Context-Correlated Structured Logs: Embedded with W3C standard 128-bit trace_id and 64-bit span_id to allow instant bi-directional correlation between terminal server logs and Jaeger traces.

1. Description of the OpenTelemetry Implementation

1.1 Architectural Overview

HydroPond AI is an asynchronous GIS and hydrological decision-support platform designed to delineate catchment watersheds and calculate harvestable rainwater yield for rural village storage ponds. The computational pipeline processes complex geospatial vector data and high-resolution raster matrices.

Without instrumentation, this pipeline operates as a black box: slow requests cannot be attributed to specific algorithms, transient external network delays (e.g., historical climate API queries) remain invisible, and memory allocation spikes cannot be correlated with grid cell dimensions.

1.2 Telemetry Subsystem Implementation Details

The implementation resides in a modular telemetry subsystem (app/telemetry.py), ensuring clean separation of concerns and zero tight coupling with business logic:

  1. Tracer Provider (TracerProvider): Configured with a standardized Resource descriptor identifying the service name (hydrology-pond-system), semantic version (2.0.0), and deployment environment. Attaches a BatchSpanProcessor coupled to OTLPSpanExporter(endpoint="http://10.1.75.51:4318/v1/traces") to asynchronously dispatch spans to the Jaeger collector without blocking the main event loop.
  2. Custom Span Hierarchy: Every algorithmic phase is instrumented with explicit child spans (tracer.start_as_current_span), creating a rich call tree: api.analyze_contour, kml.parse, dem.build, terrain.priority_flood_fill, pond.select_and_delineate, hydrology.calculate, and hydrology.fetch_historical_rainfall.
  3. Domain-Specific Semantic Attributes: Custom spans record critical hydrological attributes: hydrology.annual_rainfall_mm, hydrology.runoff_coefficient, hydrology.runoff_volume_m3, catchment.area_hectares, catchment.mean_slope_pct, and dem.cell_count.
  4. Metrics Subsystem: Registers a PrometheusMetricReader providing a native Prometheus pull endpoint at GET http://10.1.75.51:3317/metrics with custom instruments: hydrology_requests_total (Counter), hydrology_algorithm_duration_seconds (Histogram), hydrology_dem_grid_cells_total (Histogram), and hydrology_active_requests (Gauge).
  5. Trace-Context Correlated Structured Logging: Implemented a custom TraceContextFormatter subclassing Python's standard logging.Formatter. Automatically inspects trace.get_current_span().get_span_context() to inject trace_id and span_id into all log records, enabling instant bi-directional correlation between log lines and Jaeger traces.

4. Understanding of the Collected Data & Benefits for System Monitoring

4.1 Latency Profiling & Algorithmic Bottleneck Localization

From the Jaeger waterfall trace in Figure 3, we obtain a precise time budget for the 4.88 s execution:

  1. DEM Rasterization (dem.build, 60.2% of total time): SciPy bivariate interpolation over 86,390 cells takes 2.94 s. This identifies griddata interpolation as the primary computational bottleneck. Optimization action: Pre-compiling Delaunay triangulation or utilizing GPU-accelerated CuPy interpolation.
  2. External API Latency (hydrology.fetch_historical_rainfall, 20.4% of total time): The outgoing HTTP request to Open-Meteo took 997.34 ms. Optimization action: Caching daily rainfall sums in an in-memory Redis layer keyed by coordinate geohash to eliminate remote round trips.
  3. Depression Filling (terrain.priority_flood_fill, 13.7% of total time): The Barnes/Wang-Liu heap algorithm took 667.98 ms on an 86,390-cell grid. Optimization action: Implementing early termination or hierarchical grid coarsening.
  4. Pond Site Selection & Delineation (pond.select_and_delineate, < 1% of total time): Heuristic candidate evaluation and BFS upstream graph traversal took only 36.97 ms, confirming high algorithmic efficiency.

4.2 Proactive Capacity Planning & Operational Reliability

Prometheus time-series metrics enable data-driven capacity decisions:

  • Throughput & Cache Efficiency: Figure 5 proves that 60% of /api/sample-contours requests are served from cache in < 45 ms, protecting backend memory from redundant re-computations.
  • Water Volume Aggregates: Tracking cumulative volume via hydrology_water_volume_harvestable_m3 allows regional planners to monitor total water capacity planned across multi-village jurisdictions.
  • SLA & Health Monitoring: Setting automated Prometheus alert rules on http_requests_total error rates (5xx > 1%) and hydrology_algorithm_duration_seconds (p95 > 3 s) allows automated alerting before users experience degraded service.

4.3 Root-Cause Analysis via Cross-Pillar Correlation

Prior to OpenTelemetry, troubleshooting an exception required manually cross-referencing server timestamps with client bug reports. With correlated logging and tracing:

  • If an invalid polygon geometry causes a topology error, the log line prints the exact trace_id.
  • Clicking the trace in Jaeger reveals the exact polygon vertices (request.polygon_vertices), the elevation grid dimension, and the exact stack trace recorded by span.record_exception(exc) on the failed span.

5. VIVA Examination Preparation & Key Concepts

Question Model Viva Answer
Why use OpenTelemetry instead of writing print statements or loggers? Print statements and logs lack distributed causality. OpenTelemetry standardizes context propagation using W3C Trace Context headers, linking distributed spans across microservices and providing structured metrics that can be queried mathematically with PromQL, rather than parsed as raw text.
What is the difference between OpenTelemetry, Jaeger, and Prometheus? OpenTelemetry is the instrumentation framework that collects observability data. Jaeger is a distributed tracing backend that visualizes call trees and waterfalls. Prometheus is a time-series database that periodically pulls numeric metrics for dashboard graphing and alerting.
What is the difference between a Trace and a Span? A Trace represents the entire journey of a single request through the system from start to finish. A Span represents a single unit of contiguous work within that trace (e.g. dem.build), with a name, timestamps, attributes, and optional events.
How did you correlate logs with traces in your project? We implemented a custom TraceContextFormatter that extracts trace_id and span_id from trace.get_current_span().get_span_context() during log formatting. This guarantees that every log output in app.log contains the exact 128-bit Trace ID displayed in Jaeger.
What was the biggest performance bottleneck discovered by tracing? The Jaeger flamegraph revealed that SciPy elevation grid interpolation (dem.build) accounted for 60.2% (2.94 s) of the total 4.88 s transaction, whereas pond selection and catchment graph traversal took only 36.97 ms.
